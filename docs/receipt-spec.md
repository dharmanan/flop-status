# Receipt Specification v0.1

## Purpose

A receipt is the portable evidence object produced by Capability Lab after a completed verification run.

Its primary job is to bind:

* agent DID
* capability and trial
* exact challenge
* exact submitted result
* verifier identity and version
* verdict
* issue time
* Capability Lab attestation signature

## Receipt lifecycle

Receipts are immutable.

Historical receipts are never edited when a trial or verifier changes. A new verification produces a new receipt.

MVP public capability evidence is based on PASS receipts.

## Required fields

```json
{
  "receipt_version": "1",
  "receipt_id": "...",
  "agent_did": "did:key:...",
  "capability_id": "...",
  "trial_id": "...",
  "trial_version": "...",
  "challenge_id": "...",
  "challenge_hash": "...",
  "result_hash": "...",
  "verifier_id": "...",
  "verifier_version": "...",
  "verdict": "PASS",
  "evidence_type": "DETERMINISTICALLY_VERIFIED",
  "issued_at": "...",
  "server_key_id": "...",
  "server_signature": "..."
}
```

Optional extension:

```json
{
  "technocore_reference": "..."
}
```

## Identifier requirements

### receipt_id

Globally unique opaque identifier generated by Capability Lab.

It must not carry security meaning.

### challenge_id

References the exact one time challenge instance.

### capability_id

Stable semantic capability identifier.

### trial_id and trial_version

Together identify the exact trial contract used.

### verifier_id and verifier_version

Together identify the exact deterministic verification behavior used.

## Hash requirements

### challenge_hash

SHA256 of the canonical challenge payload used by the verifier.

### result_hash

SHA256 of the canonical submitted result payload used by the verifier.

The canonicalization rule must be documented and versioned before implementation.

Do not hash ad hoc runtime JSON serialization if object key ordering or serialization behavior can vary.

## Server signature

The receipt payload excluding `server_signature` is canonicalized and signed with the active Capability Lab Ed25519 attestation key.

`server_key_id` identifies the corresponding public key.

Historical public keys must remain available after rotation.

## Verdict

Initial receipt verdict vocabulary:

PASS
FAIL
UNKNOWN

For MVP public verified capability records, only PASS maps to DETERMINISTICALLY_VERIFIED evidence.

FAIL receipts may be stored for audit and user history but are not required to be publicly listed.

UNKNOWN must never be presented as failed capability evidence.

## Evidence type

Initial values:

CLAIMED
UNTESTED
DETERMINISTICALLY_VERIFIED
PEER_VERIFIED
UNKNOWN

The initial deterministic MVP issues DETERMINISTICALLY_VERIFIED only for PASS.

## Verification procedure

A third party receiving a receipt should be able to:

1. parse the receipt version
2. obtain the public key for `server_key_id`
3. canonicalize the unsigned receipt payload according to that receipt version
4. verify `server_signature`
5. inspect challenge and result hashes
6. inspect trial and verifier versions

Signature validity proves that Capability Lab attested to the receipt payload.

It does not independently prove that the verifier implementation was correct. Published verifier specifications or reproducible verifier packages can strengthen this later.

## Public verification page

The public page should expose at minimum:

* Receipt ID
* Agent DID
* Capability
* Trial
* Trial version
* Verdict
* Evidence type
* Challenge hash
* Result hash
* Verifier id
* Verifier version
* Issued time
* Server key id
* Receipt signature status
* Optional Technocore reference

Primary status wording for a valid PASS receipt:

`Receipt signature: VALID`

## Key rotation

A rotation creates a new server key id.

New receipts use the new active key.

Old receipts continue to verify with their historical key.

The application must not silently replace the key id on an existing receipt.

## Key compromise boundary

If an attestation private key is confirmed compromised, Capability Lab must publish revocation or compromise metadata before claiming trust in receipts issued by that key during the affected period.

The exact public transparency mechanism is deferred until before public launch.

## Offline verification scope

MVP target:

A receipt file plus historical Capability Lab public key material is sufficient to verify receipt integrity and attestation signature offline.

MVP does not require full offline re execution of the original deterministic verifier.

Future verifier publication may add that capability.

## Compatibility rule

Any change that alters canonical receipt bytes, signature semantics, required field meaning or verification procedure requires a new `receipt_version`.
