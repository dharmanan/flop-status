# Trial 1 Vertical Slice Implementation Specification v0.1

## Purpose

This document defines the first implementation milestone for FLOP Capability Lab.

The milestone is intentionally narrow:

Identity → Challenge → Signed Submission → Deterministic Verification → PASS → Server Signed Receipt → Public Verification

No second trial, broad dashboard, Technocore dependency, wallet, LLM judge or messaging feature is allowed into this milestone.

## Definition of done

Trial 1 is complete only when a clean browser can create or connect an Ed25519 `did:key`, receive a unique challenge, submit a DID signed result, receive a persisted PASS receipt, refresh without losing state, and open the public receipt URL in a separate clean browser where the Capability Lab receipt signature verifies as VALID.

Technocore may be completely unavailable during this acceptance path.

## Trial identity

Capability id:

`cryptography.signature-verification`

Trial id:

`ed25519-signature-verification`

Trial version:

`1`

Verifier id:

`ed25519-signature-verifier`

Verifier version:

`1`

Evidence type on PASS:

`DETERMINISTICALLY_VERIFIED`

## Supported agent identity for milestone 1

Only Ed25519 `did:key` agent identities are accepted.

The server must decode the multibase value, decode the multicodec prefix, require Ed25519 public key type, require a 32 byte raw public key, and use that public key to verify the submission signature.

Other DID methods and other key types are out of scope for this milestone and must return a typed unsupported identity error rather than being guessed or partially accepted.

Reference: https://w3c-ccg.github.io/did-key-spec/

## Canonicalization contract

All cryptographically signed JSON payloads in this milestone use RFC 8785 JSON Canonicalization Scheme.

Canonicalization id:

`jcs-rfc8785-v1`

All cryptographic operations use UTF-8 bytes of the RFC 8785 canonical representation.

Do not use runtime object insertion order, pretty printed JSON, ad hoc key sorting or unversioned `JSON.stringify` output as a signing contract.

Reference: https://www.rfc-editor.org/rfc/rfc8785.html

## Common encoding rules

Hash algorithm:

`SHA-256`

Hash text format:

`sha256:<base64url-no-padding>`

Signature text format:

`base64url-no-padding`

Timestamps:

UTC RFC 3339 strings produced by the server.

Opaque ids:

Application generated UUIDs represented as lowercase strings.

The database must not derive authorization or trust from identifier ordering.

## Challenge issuance

Endpoint:

`POST /api/v1/challenges`

Request payload:

```json
{
  "agent_did": "did:key:...",
  "trial_id": "ed25519-signature-verification"
}
```

Requirements:

1. validate that the DID is a supported Ed25519 `did:key`
2. reject a second active unexpired challenge for the same DID and trial
3. generate a cryptographically random challenge id and nonce
4. generate one Ed25519 signature verification case
5. bind the challenge to the requesting DID, trial id and trial version
6. set `issued_at` from server time
7. set `expires_at` to ten minutes after issuance
8. persist the hidden verifier ground truth separately from the public challenge payload
9. calculate and persist the RFC 8785 challenge hash
10. return only the public challenge representation

## Trial 1 challenge construction

The challenge asks the agent to judge whether a supplied Ed25519 signature is valid for a supplied message and public key.

Public challenge payload:

```json
{
  "challenge_version": "1",
  "challenge_id": "...",
  "agent_did": "did:key:...",
  "capability_id": "cryptography.signature-verification",
  "trial_id": "ed25519-signature-verification",
  "trial_version": "1",
  "nonce": "...",
  "case": {
    "algorithm": "Ed25519",
    "public_key": "...",
    "message": "...",
    "signature": "..."
  },
  "issued_at": "...",
  "expires_at": "..."
}
```

The case public key, message and signature encodings must be explicitly documented in the API schema. For milestone 1, binary values use base64url without padding.

## Challenge case generation

The generator must support at least two classes:

`VALID_SIGNATURE`

`INVALID_SIGNATURE`

A valid case contains a signature generated by the matching test private key over the exact message bytes.

An invalid case must be generated from a known valid case by a controlled mutation that leaves the payload structurally valid but makes cryptographic verification false. Examples include changing one message byte or changing one signature byte.

Do not create invalid cases by malformed base64, wrong key length or schema errors. Those test parsing, not signature verification capability.

The server stores hidden expected data such as:

```json
{
  "expected_valid": true,
  "case_class": "VALID_SIGNATURE"
}
```

This hidden verifier context is never returned by the challenge API.

## Agent result schema

The result for Trial 1 is deliberately small:

```json
{
  "valid": true,
  "reason_code": "SIGNATURE_VALID",
  "message_hash": "sha256:..."
}
```

Allowed reason codes:

`SIGNATURE_VALID`

`SIGNATURE_INVALID`

`message_hash` is SHA-256 of the exact decoded message bytes from the challenge.

The verifier checks all three fields.

A correct boolean with an incorrect message hash is FAIL because the submitted result is not bound strongly enough to the exact message presented in the challenge.

## Signed submission envelope

Endpoint:

`POST /api/v1/challenges/:challengeId/submissions`

Request shape:

```json
{
  "payload": {
    "submission_version": "1",
    "canonicalization": "jcs-rfc8785-v1",
    "challenge_id": "...",
    "challenge_hash": "sha256:...",
    "agent_did": "did:key:...",
    "trial_id": "ed25519-signature-verification",
    "trial_version": "1",
    "result": {
      "valid": true,
      "reason_code": "SIGNATURE_VALID",
      "message_hash": "sha256:..."
    },
    "submitted_at": "..."
  },
  "signature": {
    "algorithm": "Ed25519",
    "encoding": "base64url",
    "value": "..."
  }
}
```

The client signs RFC 8785 canonical UTF-8 bytes of `payload` only.

`submitted_at` is client supplied and signed for audit purposes. It is never trusted for expiry. Challenge expiry uses server time.

## Submission validation order

The server performs these checks in this order before a verdict can exist:

1. payload size within configured limit
2. strict JSON schema validation
3. path challenge id equals payload challenge id
4. challenge exists
5. challenge DID equals payload DID
6. trial id and version equal the challenge record
7. supplied challenge hash equals persisted challenge hash
8. challenge state is `ISSUED`
9. server time is before `expires_at`
10. DID is supported Ed25519 `did:key`
11. DID signature over canonical payload is valid

Failures in steps 1 through 10 are request or identity errors. They are not capability FAIL verdicts.

Only after the signed submission is accepted may the deterministic trial verifier produce PASS or FAIL.

## Challenge consumption transaction

Submission consumption must be race safe.

Recommended transaction:

1. begin transaction
2. lock challenge row for update
3. recheck state and expiry under the lock
4. insert the immutable submission row with a unique constraint on `challenge_id`
5. update challenge state from `ISSUED` to `SUBMITTED`
6. commit

If two requests race, exactly one may consume the challenge.

A duplicate request after successful consumption must not create a second submission.

## Verification execution

After the submission has been durably persisted, run the deterministic verifier against:

1. persisted public challenge payload
2. persisted hidden verifier context
3. persisted result payload

The verifier returns a typed object such as:

```json
{
  "verdict": "PASS",
  "reason_code": "EXPECTED_RESULT_MATCH",
  "verifier_id": "ed25519-signature-verifier",
  "verifier_version": "1"
}
```

Expected comparisons:

1. `result.valid` equals hidden `expected_valid`
2. `reason_code` matches the boolean meaning
3. `message_hash` equals SHA-256 of the challenge message bytes

The verifier must not call Technocore, an LLM or any external API.

## Verification persistence

Persist every executed verification run.

If the deterministic verifier executes normally and the result is correct:

`PASS`

If the deterministic verifier executes normally and the result is incorrect:

`FAIL`

If infrastructure prevents a trustworthy verifier result from being produced:

`UNKNOWN`

An exception, database failure or unavailable optional integration must never be converted into FAIL.

## PASS transaction

For PASS:

1. create immutable verification run
2. construct unsigned receipt payload
3. RFC 8785 canonicalize the unsigned receipt payload
4. sign it with the active Capability Lab Ed25519 attestation key
5. insert immutable receipt
6. update challenge state to `PASS`
7. commit atomically

If this transaction fails, no partial PASS receipt may be exposed.

The receipt private signing key must not be stored in PostgreSQL.

## FAIL transaction

For FAIL:

1. create immutable verification run
2. update challenge state to `FAIL`
3. commit

Milestone 1 does not require a public FAIL receipt.

## UNKNOWN transaction

For UNKNOWN:

1. persist the verification run when possible
2. update challenge state to `UNKNOWN` when possible
3. do not create DETERMINISTICALLY_VERIFIED evidence
4. do not expose UNKNOWN as capability failure

A stored submission may be reprocessed internally after an UNKNOWN infrastructure outcome. The client must not submit the same challenge again.

## Lost response recovery

A successful server transaction may complete even if the HTTP response is lost.

Therefore the client must recover state through:

`GET /api/v1/challenges/:challengeId`

If the challenge is PASS, the response includes its receipt id.

The UI must never instruct the user to resubmit the same consumed challenge merely because a response timed out.

## Receipt generation

Milestone 1 follows `docs/receipt-spec.md`.

The PASS receipt binds at minimum:

agent DID

capability id

trial id and version

challenge id and hash

result hash

verifier id and version

verdict

evidence type

server key id

issue time

server signature

The result hash is SHA-256 of RFC 8785 canonical UTF-8 bytes of the persisted Trial 1 `result` object.

## Server signing key

Milestone 1 uses one Ed25519 attestation key.

PostgreSQL stores only public metadata.

The private key is supplied through the deployment secret store.

A stable `server_key_id` identifies the public key.

`GET /api/v1/server-keys` exposes enough public material to verify receipts.

## Public verification

Public route:

`/verify/:receiptId`

Public API:

`GET /api/v1/verification/:receiptId`

The verification page independently checks the Capability Lab receipt signature using public server key material.

Minimum visible fields:

Receipt ID

Agent DID

Capability

Trial and version

Verdict

Challenge hash

Result hash

Verifier and version

Issued time

Server key id

`Receipt signature: VALID` or an explicit invalid state

The page requires no login and no local agent key.

## Capability record update

For milestone 1, public verified capability state is derived from PASS receipts rather than accepted from an agent profile claim.

A PASS receipt for this trial increments the demonstrated trial count for:

`cryptography.signature-verification`

Claims and PASS evidence must remain visually and semantically distinct.

## Technocore boundary

No core module in this vertical slice may require a Technocore read or write.

Optional Technocore publication can be added later downstream of a completed receipt.

A Technocore failure must not alter a stored PASS receipt.

## Required error vocabulary

At minimum expose typed application errors for:

`UNSUPPORTED_DID`

`INVALID_DID`

`ACTIVE_CHALLENGE_EXISTS`

`CHALLENGE_NOT_FOUND`

`CHALLENGE_EXPIRED`

`CHALLENGE_ALREADY_CONSUMED`

`CHALLENGE_BINDING_MISMATCH`

`INVALID_SUBMISSION_SCHEMA`

`INVALID_AGENT_SIGNATURE`

`VERIFICATION_UNKNOWN`

Do not map these errors to capability FAIL unless the deterministic trial verifier actually executed and returned FAIL.

## Stop conditions

Stop implementation and fix the model before adding Trial 2 if any of the following are true:

1. the same challenge can create two submissions
2. a different DID can submit for the challenge
3. an expired challenge can PASS
4. a modified signed payload can verify
5. a modified receipt can verify
6. PASS can exist without a persisted verification run
7. a public receipt disappears after refresh or process restart
8. Technocore unavailability breaks core verification
9. UNKNOWN appears as FAIL
10. the second clean browser cannot verify the receipt signature
